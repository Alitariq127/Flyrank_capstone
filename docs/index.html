FlyRank Search Intelligence Capstone · Refresh / Content Opportunity Scoring

Which pages should a content team review this sprint, and why?

Abstract. We ask which pages in a search-visibility warehouse are worth a content team's attention this sprint. Using a strict time-split (12-week feature window, held-out future label window, and a fully separate final test window), we label pages as growing, declining, or stable based on click trend, engineer safe on-page and behavioral features, and compare a gradient-boosted classifier against a simple trend-slope baseline. The model reaches 53.6% held-out accuracy versus an estimated 36.8% baseline on the validation split, driven mostly by better identification of stable pages. We convert predictions into a ranked, reason-coded action list — 101 pages flagged for review out of 500 — rather than a bare classification score.

Introduction

A content or SEO team can't manually review every page every sprint. The practical decision this work supports is: given limited review capacity, which pages should be looked at first, and what should the review actually check for? A page flagged "declining, still ranks in the top 10, hasn't been refreshed in 2+ years" is a different priority — and a different task — than one flagged "declining, ranks poorly, thin content." The goal here is a ranked action list a team could plausibly work from, not just a label.

Data

This paper works against the FlyRank ML Internship search-visibility warehouse schema — one row per page per week, with clicks, impressions, click-through rate, average ranking position, word count, content category, and days since publish. No client names, domains, raw URLs, or private query strings are used or shown anywhere in this analysis; all page identifiers here are anonymized indices.

Note on this version of the analysis: the pipeline below is built and validated end-to-end against synthetic data generated to match the warehouse schema, as a demonstration of the full method. The single swap-in point to run this on the real warehouse is documented in the repo's _lib.py — replacing one data-loading function with a DuckDB query over the real hf:// release. No other part of the pipeline changes.

Windows used: weeks 0–11 for features, weeks 12–15 as a held-out label window (used only to compute training/validation labels — never touched for features), and weeks 16–19 as a fully separate final test window, untouched until the last evaluation step.

Methodology

Label definition

Primary metric: clicks. Within the label window, we compare the early half against the late half; a page is growing if late-window clicks exceed early-window clicks by 15% or more, declining if the reverse, and stable otherwise. The 15% threshold (rather than 0%) is a deliberate choice to avoid mistaking week-to-week noise for a real trend.

Features

All computed strictly from the feature window: average clicks, impressions, CTR, and position; click volatility (std. dev.); a within-window trend slope; word count; content category (one-hot); and days since publish.

Baseline and model

Baseline: a simple rule — declining if trend slope is meaningfully negative, growing if meaningfully positive, stable otherwise. No learning involved. Model: a gradient-boosted tree classifier (scikit-learn GradientBoostingClassifier), trained on the same features, evaluated on the same split.

Validation design

Split is group-aware (by page — no page appears in both train and validation) and the label/feature windows are already time-separated, so no page's future leaks into its own features. A leakage assertion runs at the top of the pipeline, checking the three windows (feature / label / test) are pairwise disjoint before any modeling begins.

Limitations & honest framing

  • Synthetic data. All numbers above are on synthetic data built to match the real schema, not the live FlyRank warehouse — treat these as a validated method, not validated findings, until re-run on real data.
  • Directional, not causal. A "declining" label describes an observed click pattern in the label window, not a diagnosis of why — the reason codes point at correlated signals (position, CTR, content age), not confirmed causes.
  • Growing/declining recall is weak (17–29%). The model is meaningfully better than baseline mostly by getting "stable" right more often; it's a decision-support signal for prioritizing review, not a high-confidence classifier for the minority classes that matter most.
  • "Recovering" label not yet wired into this pass. The design calls for a "recovering" state (declining last period, growing now), which requires comparing two consecutive label windows. The current pipeline computes a single label window; recovering detection is defined in code (_lib.mark_recovering) but not yet exercised end-to-end — flagged here rather than silently dropped.
  • 15% threshold is a judgment call, not derived from the data's noise floor — worth revisiting once real variance is observed.
