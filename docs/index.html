FlyRank Search Intelligence Capstone · Refresh / Content Opportunity Scoring

Which pages should a content team review this sprint, and why?

Abstract. We ask which pages in a search-visibility warehouse are worth a content team's attention this sprint. Using a time-split validation design (a feature window and a strictly later, held-out label window), we label pages as growing, declining, or stable based on click trend, engineer safe on-page and behavioral features, and compare a gradient-boosted classifier against a simple trend-slope baseline. On real FlyRank warehouse data, the model reaches 80% held-out test accuracy versus a 68.8% baseline that collapses to always predicting "stable." We convert predictions into a ranked, reason-coded action list — 62,805 of 146,034 pages flagged for review — rather than a bare classification score.

Introduction

A content or SEO team can't manually review every page every sprint. The practical decision this work supports is: given limited review capacity, which pages should be looked at first, and what should the review actually check for? A page flagged "declining, still ranks near the top, hasn't been refreshed in 2+ years" is a different priority — and a different task — than one flagged "declining, ranks poorly, thin content." The goal here is a ranked action list a team could plausibly work from, not just a label.

Data

This analysis runs on the real FlyRank ML Internship search-visibility warehouse: fact_content_daily_performance (daily GSC clicks, impressions, and average position per page) joined to dim_content (word count, content creation date) on client + content identifiers. No client names, domains, raw URLs, private query strings, or Google-algorithm causal claims appear anywhere in this analysis — all page identifiers are the warehouse's own anonymized hashes.

Important scope note: this run used the warehouse's smaller sample table (fact_content_daily_performance_sample.parquet), which covered only 5 days of history. That forced a compressed window design — a single-week feature window, a 2-week label window, and a 2-week held-out test window — instead of the originally planned 12/4/4-week split. This is flagged explicitly in Limitations below: it's the single biggest caveat on these results, and re-running against the full fact_content_daily_performance/ table (78.8M rows, spanning much more history) with the full 12/4/4-week design is the natural next step.

Methodology

Label definition

Primary metric: clicks. Within the label window, we compare the early half against the late half; a page is growing if late-window clicks exceed early-window clicks by 15% or more, declining if the reverse, and stable otherwise. Label balance on this data: 71.5% stable, 15.7% declining, 12.8% growing.

Features

Computed from the feature window: average clicks, impressions, CTR, and position; click volatility; a within-window trend slope; word count; and days since content creation. With only a single-week feature window in this run, the trend slope feature carries almost no signal (there's no "early half vs. late half" within one week) — see Limitations.

Baseline and model

Baseline: a rule using trend slope alone. Model: a gradient-boosted tree classifier (scikit-learn GradientBoostingClassifier), same features, same split.

Validation design

Split is group-aware (by page) and the label/feature windows are time-separated by construction, so no page's future leaks into its own features. A leakage assertion confirmed the three windows (feature: week 0; label: weeks 1–2; test: weeks 3–4) are pairwise disjoint before modeling began.

Limitations & honest framing

  • Compressed windows, the central caveat. The sample table only covered 5 days, forcing a 1-week feature / 2-week label / 2-week test design instead of the intended 12/4/4 weeks. This is very likely why trend-based features carry no signal and why baseline collapses entirely to "stable." Re-running on the full fact_content_daily_performance/ table with proper multi-week windows is the clear next step before trusting these numbers as representative.
  • Growing-page recall is near zero (1% recall, 8% precision) in both validation and test. With a 2-week label window, "growing" is likely dominated by noise rather than real momentum — consistent with the compressed-window explanation above.
  • Directional, not causal. A "declining" label describes an observed click pattern in the label window, not a diagnosis of why — reason codes point at correlated signals (position, CTR, content age), not confirmed causes.
  • Growing pages are not currently surfaced in the ranked action list. The priority-scoring logic only assigns positive priority to declining, recovering, or thin-content stable pages — growing pages get a priority score of 0 and are filtered out, even though they're labeled "protect" in principle. This is a scope gap in the current scoring function, not a data issue, and is straightforward to fix in a future pass (give growing pages a modest positive priority so they appear, lower than declining pages, in the action list).
  • A handful of avg_position values below 1 appear in the top-ranked recommendations (e.g. 0.47, 0.63) — outside the normal 1–100+ range for Google average position. This looks like a data or aggregation artifact worth investigating before treating position-based priority ranking as fully reliable, rather than a sign the page is ranking impossibly well.
  • "Recovering" label not yet exercised. Defined in code but requires comparing two consecutive label windows — not run end-to-end here given the short window budget in this pass.
  • 15% growth/decline threshold is a judgment call, not derived from this data's actual noise floor.

Reproducibility

This run was executed end-to-end in Google Colab against the real FlyRank Hugging Face warehouse (fact_content_daily_performance_sample.parquet joined to dim_content.parquet), using DuckDB to query hf:// directly. The executed notebook, full ranked recommendations (62,805 rows), and all charts above are in this repo.

  4. work/04_features_and_split.ipynb — feature engineering + group split
  5. work/05_modeling.ipynb — baseline vs. model, confusion matrix, feature importance
  6. work/06_reason_codes.ipynb — reason-code generation
